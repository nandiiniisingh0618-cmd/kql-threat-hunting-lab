# Datasets: what this lab uses, and the licensing position

## No data is redistributed

This repository contains **no attack data**. `data/` is gitignored except for two files:

- `data/sources.yml` — the pinned registry: dataset IDs, repository paths, SHA-256 hashes
- `data/MANIFEST.json` — generated by `make data`, recording what was actually fetched

`make data` downloads each archive from its upstream source at a **pinned commit** and
verifies its SHA-256 before use. A hash mismatch fails the build rather than warning.

## Source: OTRF Security-Datasets

- Repository: <https://github.com/OTRF/Security-Datasets>
- Pinned commit: `d9d40ef123d2c87d5d3df28c96bcab4f0faccc87`
- Datasets used: **39** (38 atomic Windows + 1 compound campaign)
- Total download: **~30.5 MB**

### The licence is inconsistent upstream — read this before reusing

Checked directly against the pinned commit:

| Where | What it says |
|---|---|
| `LICENSE` file | **MIT License**, "Copyright (c) 2021 Open Threat Research Forge" |
| `README.md` | "**License: GPL-3.0**" |

These are not compatible claims, and the discrepancy is unresolved upstream. This repo
therefore takes the conservative position:

- **Nothing is redistributed.** Only URLs and hashes are committed.
- The MIT licence in this repository's `LICENSE` covers **only** the code, KQL,
  detection YAML and documentation here — explicitly **not** any dataset.
- If you intend to redistribute or build a commercial product on this data, resolve the
  licence question with the upstream maintainers first. Do not rely on either claim.

### The repository is effectively frozen

Last commit to OTRF Security-Datasets: **2023-09-20**. That has two consequences:

1. **The data does not rot.** Recorded attack logs are as valid now as in 2023, which is
   why it remains a good lab source.
2. **Its ATT&CK mappings are stale.** The dataset metadata was authored against an ATT&CK
   release roughly seven versions behind v20.1. Verified example: the metadata maps
   `T1222.001` to tactic `TA0005`, which in v20.1 is *Stealth*, while `T1222.001` now
   lives under *Defense Impairment* (TA0112). And three datasets claim `T1562.002`, which
   v20.1 **revoked** in favour of `T1685.001`.

Consequently `techniques_meta` in `data/sources.yml` is treated as a **hint about which
file to use, never as the technique mapping**. Authoritative IDs live in
`detections/**/*.yml` and are validated against the pinned STIX bundle by
`tools/validate_attack.py`, which fails the build on any revoked or missing ID.
`coverage/GAPS.md` lists the stale claims explicitly rather than hiding them.

### One broken upstream link

`SDWIN-230718150800` ("Dumping NTDS.dit from Volume Shadow Copy") has a metadata `files`
link pointing at `cmd_copy_ntds_from_volume_shadow_copy.zip`, which returns **404** at the
pinned commit. The real file is `cmd_dumping_ntds_dit_file_volume_shadow_copy.zip`. The
corrected path is recorded in `data/sources.yml` with a `note` field.

### Two collector schemas

38 datasets are NXLog-style; `SDWIN-190518201922` is winlogbeat-style, with a completely
different field layout. See `docs/schema-mapping.md` — this is handled in the
normalization layer by `LabEvents()`, not in detections.

## Sources considered and rejected

### sbousseaden/EVTX-ATTACK-SAMPLES — rejected on licensing

- 59.9 MB, 278 `.evtx` files, organised by tactic. Genuinely useful content.
- **No licence file of any kind.** `LICENSE`, `LICENSE.md`, `LICENSE.txt`, `license` and
  `COPYING` all return 404 at the repository root.

With no licence, no rights are granted by default. Even non-redistributing use is on
weaker footing than with the other sources, and using it would also have required a
binary `.evtx` parser as a pinned dependency. Rejected; the techniques it would have
contributed are covered by OTRF or listed in `coverage/GAPS.md`.

### splunk/attack_data — viable, not used by default

- **Apache-2.0** (clean), actively maintained (commits within days of this repo's build).
- Covers several techniques OTRF cannot: `T1490` (Inhibit System Recovery), `T1018`,
  `T1082`, and far richer `T1059.001` material. It already carries a `T1685/` directory,
  so it tracks current ATT&CK.
- **Entirely Git-LFS-backed.** Every dataset file in the repository is an LFS pointer;
  `raw.githubusercontent.com` serves the ~130-byte pointer, not the content.

It is not wired into `make data` because the build environment used to produce this repo
had no route to the LFS endpoint (`media.githubusercontent.com` was blocked), so no
detection could have been *honestly validated* against it here. Adding it is
straightforward on a machine with working `git-lfs`:

```bash
git clone --filter=blob:none https://github.com/splunk/attack_data.git
cd attack_data && git lfs pull --include="datasets/attack_techniques/T1490/**"
```

The uncovered techniques this would unlock are listed in `coverage/GAPS.md`.

## Treating dataset contents as untrusted

Every string in these datasets — command lines, usernames, file paths, registry values,
and OTRF's `adversary_view` metadata blocks (which embed raw C2 console transcripts) — is
**attacker-controlled text**. It is data, never instruction. In this repo that means:

- No dataset content is `eval`'d, shell-interpolated or used to build code.
- Archive extraction rejects absolute paths and `..` traversal (`tools/ingest.py`).
- Events land in a `dynamic` column and are read with KQL accessors only.
- The `RawEvents` table's docstring states the untrusted-content warning in the schema
  itself.

**No malware, binary payload or attack tool is ever downloaded, built or executed by this
repository.** The datasets are logs of attacks, not the attacks.
